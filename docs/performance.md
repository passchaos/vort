# Performance evidence

Vort does not yet claim compression performance wins. This document records the
benchmark protocol and the current bootstrap benchmark surface so future claims
can be tied to reproducible evidence.

The checksum smoke benchmark processes a deterministic 1 MiB buffer repeatedly
through Adler-32, CRC-32 scalar, CRC-32 slice-by-4, CRC-32 slice-by-8, CRC-32 slice-by-16, CRC-32 best dispatch, CRC-32C scalar, CRC-32C slice-by-8, CRC-32C slice-by-16, and CRC-32C best dispatch paths and reports aggregate MiB/s plus selected checksum dispatch names; it also emits per-algorithm CSV rows so zlib Adler-32 and gzip CRC-32 wrapper bottlenecks can be tracked separately from inflate throughput, and `bench-checksum-csv` writes those rows to `zig-out/vort-checksum-bench.csv`. Each iteration perturbs and restores one input byte and marks the digest as used, keeping ReleaseFast runs from folding repeated checksum calls into a constant. The deflate decode smoke benchmark repeatedly decodes representative raw/zlib/gzip fixed and dynamic samples, reports allocator-returning, exact-size allocation, and caller-buffer rows for each sample, includes fixed-Huffman literal/distance lookup fast paths, and emits dynamic-block stage rows for length parsing, literal-table construction, distance-table construction, payload decode, and total caller-buffer decode on the small dynamic sample. Huffman fast-decode evidence should be read from ReleaseFast runs because the optimized path records maximum code widths and resumes long-code fallback after the lookup width rather than replaying short widths on each miss. `run-deflate-decode-stage-report` isolates raw/zlib/gzip alloc, exact-size alloc, and caller-buffer decode overhead; its dashboard writes CSV/Markdown plus schema-checked JSON, and the JSON/Markdown artifacts carry an error-path smoke table for malformed, truncated, checksum-mismatched, and concatenated-gzip boundary inputs. The timing rows now include first raw-DEFLATE block diagnostics (`raw_block_type`, consumed header bits/bytes, and dynamic HLIT/HDIST/HCLEN plus literal/distance non-zero, zero, and max-bit counts) so text-heavy decode regressions can be separated from dynamic-header shape before changing Huffman table policy. `run-deflate-huffman-build-bench-gate` writes and validates `zig-out/vort-deflate-huffman-build-bench.csv`, isolating HuffmanTable and FastDecoder construction cost for literal, distance, and code-length alphabets before table setup changes; FastDecoder initialization now uses lookupCoverage to preserve the no-memset path for fully-covered tables while avoiding the old double-fill work for partial dynamic tables; `run-deflate-huffman-lookup-bench-gate` writes and validates `zig-out/vort-deflate-huffman-lookup-bench.csv`, isolating Huffman symbol decode throughput for fixed literals, fixed distances, code-length symbols, dynamic mixed/long-tail literal shapes, and dynamic distance shapes across the compact table decoder and FastDecoder lookup widths 5/8/9/11/12; use it before changing fast-table width selection, miss fallback, or fixed-Huffman lookup code. `run-deflate-chunked-huffman-bench-gate` adds the same Huffman decode shapes over buffered, 4 KiB, 64-byte, and 1-byte chunked readers for fixed literals and dynamic literal fast tables, plus coalesced 4 KiB/64-byte/1-byte rows that pre-join the same chunks into a contiguous buffer before timing `BufferedBitReader`, joined 4 KiB/64-byte/1-byte rows that include the per-iteration copy cost, `windowed1024_*` / `windowed4096_*` prototype readers that refill 1 KiB or 4 KiB staging windows from chunks, and `span_*` prototype readers that keep a current chunk slice/local offset and feed the bit buffer directly from that span. Together these expose the combined `hasBits`/peek/advance reader cost that plain Huffman lookup rows hide and bracket bounded-refill/coalescing designs before changing production decode; the first `windowed1024_*` and `windowed4096_*` smokes are intentionally evidence-only because their naive per-byte bit staging did not reliably beat the current chunked reader, despite larger windows sometimes helping isolated rows; the `span_*` rows are also benchmark-only but are a stronger production-candidate signal because per-chunk span/local-offset feeding is much closer to joined/coalesced throughput on dynamic rows. A direct production A/B that added a `staged_local` offset to `ChunkedBitReader.fill`, trying to transfer the span idea into the existing absolute-offset reader, was rejected: chunked Huffman was mixed and `run-chunked-zlib-bench-report -- --repeat 1 --iterations 800` against `921c01f` showed median direct ratios around `0.846x` for `png-rgb8-literal-large-4k`, `0.852x` for `png-rgb8-match-large-4k`, and `0.978x` for the stored-direct row. The benchmark-only span result therefore points to a deeper reader-shape rewrite, not a small staged-local patch. A follow-up isolated `ChunkedSpanBitReader` production candidate, wired only into chunked zlib direct decode, kept the existing public reader intact while using a per-chunk slice/local-offset state internally; ReleaseFast A/B against `59edd4c` on `run-chunked-zlib-bench-report -- --repeat 1 --iterations 800` improved true chunked-reader direct throughput by about `1.171x` on `png-rgb8-literal-large-4k` and `1.167x` on `png-rgb8-match-large-4k`, while the stored-direct row stayed roughly neutral (`0.997x`). The same span reader now backs PNG streaming chunked zlib decode as well; ReleaseFast A/B against `b51d9d8` on `run-png-streaming-zlib-bench-report -- --repeat 3 --iterations 1000` improved chunked rows by about `1.09x` for dynamic RLE, `1.01x` for row-repeat dynamic, and `1.05x` for row-repeat fixed, with small-distance dynamic mixed/slightly negative in the short median probe. PNG small-distance pending matches now use a seed-and-doubling copy for length >=16 instead of repeating 2/3/4-byte stores; ReleaseFast A/B on the same PNG streaming benchmark improved `png-stream-small-distance-dynamic` chunked throughput by about `1.107x` while RLE and row-repeat rows stayed roughly neutral. PNG streaming pending matches with overlapping distances greater than four now also seed one distance window from the history ring and then use the destination-row doubling copy; ReleaseFast A/B on `run-png-streaming-zlib-bench-report -- --repeat 3 --iterations 800` moved row-repeat dynamic/fixed rows from about `153.33` / `154.61` MiB/s to about `1208.80` / `1224.76` MiB/s for contiguous decode and from about `153.63` / `152.97` MiB/s to about `1174.51` / `1177.64` MiB/s for chunked decode. Lowering the threshold to 8 bytes was tested and rejected after the PNG streaming smoke showed no clear small-distance gain and a row-repeat dynamic regression, so the 16-byte cutoff remains. The chunked zlib allocating unknown-size path now uses the same span reader, preserving the existing allocation-count tests while avoiding the old chunked bit reader for API callers that request owned output from chunks. ZlibDecoder direct chunked reset paths now reuse the already-computed chunk total when installing frame length, avoiding a second chunk-length scan after successful direct decode. A follow-up attempt to localize `ChunkedSpanBitReader.fill` state into stack variables was rejected: zlib direct rows were mixed and PNG streaming chunked rows regressed sharply in the short A/B, so the simpler field-based span fill remains in production. Generic FastDecoder paths now check the reader's staged reservoir after the mandatory padded peek instead of recomputing total remaining bits on the buffered/chunked hot path; the fixed Huffman specialized helpers keep the older `hasBits` check after A/B exposed noisy fixed-code rows. The local ReleaseFast A/B of `vort-deflate-chunked-huffman-bench --iterations 256` showed about `1.025x` median geomean overall and about `1.039x` on dynamic rows, with the clearest wins on 4 KiB/64-byte chunk rows while 1-byte rows remain noisy and still need a broader direct-reader redesign. Chunked zlib/PNG paths that already computed total compressed length now initialize `ChunkedBitReader` with that known total to avoid a second chunk-length scan; the focused true `chunked-reader` row A/B on `png-rgb8-literal-large-4k` measured about `1.021x` median and `1.033x` geomean on direct throughput. The zlib chunk footer validator now uses the known total length to read the common final Adler-32 from the tail chunks instead of scanning forward from chunk zero; a focused A/B against `b1a9d3d` on the same true chunked-reader row measured about `1.038x` median and `1.069x` geomean direct throughput, while split-footer tests cover empty chunks and multi-chunk footers. A later attempt to reuse that first deflate block-type probe to skip the stored-direct attempt on non-stored large streams was rejected: short ReleaseFast A/B against `8baae19` was mixed to negative, with median direct ratios around `0.979x` for the literal true-chunked row, `0.984x` for the match-heavy true-chunked row, and `0.984x` for the stored-direct row. A follow-up dynamic literal lookup policy A/B kept max-bit 10 blocks on the existing 11-bit table after a `<=10` cutoff regressed the binary row, but moved max-bit <=9 blocks to the cheaper 9-bit table; the ReleaseFast repeat3 stage report improved caller-buffer zlib rows for text/dynamic-match/structured while preserving the max-bit-10 binary policy. `run-deflate-dynamic-decode-profile-csv` writes `zig-out/vort-deflate-dynamic-decode-profile.csv` with dynamic payload counters for literal/match counts, literal/distance fast-table hit/miss ratios, fast-table lookup coverage/size ratios, match-copy class byte ratios/dominant class, per-class extra-bit attribution, and length/distance extra-bit reads; `run-deflate-extra-bits-bench-gate` writes and validates `zig-out/vort-deflate-extra-bits-bench.csv`, isolating contiguous, legacy chunked, and span-reader extra-bit throughput for 1/3/5/9/13-bit widths across 4 KiB, 64-byte, and 1-byte chunks before production bitreader changes; span rows show the new reader also improves length/distance extra-bit reads rather than only Huffman-symbol lookup; ChunkedBitReader fill now avoids re-running full staged-cursor synchronization while the staged byte remains inside the cached chunk, a narrow A/B that improved the large literal-coded chunked-reader row by about `1.069x` (`133.92 -> 143.22` MiB/s) and direct geomean by about `1.018x` on the chunked zlib repeat5 benchmark; A similar consumed-cursor fast path in `advanceBitsStagedAssumeAvailable` was rejected: the extra-bit microbenchmark regressed sharply across 4 KiB, 64-byte, and 1-byte chunk rows, showing that the added per-advance branch was more expensive than the existing `syncCursor` call pattern. A narrower chunk-local multi-byte staging attempt inside `fill` was also rejected: it regressed the extra-bit gate across all chunk sizes, with geomean ratios around `0.73x` for 4 KiB/64-byte chunks and `0.71x` for 1-byte chunks, so the one-byte staging loop with the staged-cursor guard remains the production path. a chunked-reader fill batching experiment was measured against that gate and rejected because chunked_64/chunked_1 regressed for most widths despite isolated gains at 13-bit chunked_64 and 3-bit chunked_1; `run-deflate-match-copy-bench-gate` writes and validates `zig-out/vort-deflate-match-copy-bench.csv`, a focused microbenchmark for current, non-overlap-first, and small-unrolled match-copy kernels across RLE, small-distance, non-overlapping, and overlapping cases; `run-deflate-dynamic-decode-profile-gate` validates the README/roadmap rows and histogram/top-symbol consistency and is included in `ci-smoke`. The current README/roadmap/chunked-window-match profile shows literal misses are effectively zero while distance fast-table misses are low single-digit percentages; the gate now requires the chunked-window-match synthetic row to exceed the stack-join raw threshold, be match-heavy, and be non-overlap dominated so true chunked-reader match/history costs remain visible beside the literal-only throughput row. It also shows high extra-bit density on text-heavy matches (about `7.92` bits per README match and `9.70` bits per roadmap match), and now includes semicolon-delimited length/distance symbol histograms, top-3 symbol summaries, and extra-bit-width read/bit histograms so those extra-bit costs can be traced to specific DEFLATE code ranges (current README top distance symbols include `12:152`, `13:105`, `20:101`, while top distance extra-bit costs are `28:949`, `20:909`, `22:790`; roadmap count leaders are `26:540`, `28:516`, `24:512`, and extra-bit cost leaders are `28:6708`, `26:6480`, `24:5632`). The remaining gap likely needs bitreader/extra-bit, table setup, and payload-loop evidence beyond simple fast-table width tweaks. The repeat3 stage report also appends `README.md` and `docs/roadmap.md` via `--builtins-plus-files`, keeping the known text-heavy weak cases visible beside the built-in smoke corpus. `run-chunked-zlib-bench-report-gate` validates the repeat3 CSV for contiguous zlib decode, legacy join-then-decode chunks, and direct chunked zlib decode on PNG-like payloads with fixed-size and tiny/empty IDAT-style chunks; the CSV now includes `direct_strategy` so direct-API rows distinguish `stack-join`, `stored-direct`, legacy `chunked-reader`, and current `span-reader` execution before accepting small chunked-reader changes; the benchmark includes large literal-coded and match-heavy rows that exceed the bounded stack-join limit so true chunked-reader throughput stays visible across both pure literal and match-copy dynamic payloads. `run-chunk-cursor-bench-gate` adds a lower-level CSV for read-byte and copy-to cursor kernels across one-byte empty, seven-byte empty, and 256-byte chunk layouts so cursor micro-optimizations can be evaluated before re-running full zlib decode. The direct chunked path still uses a bounded stack join for small compressed non-stored members when that beats cursoring through thousands of tiny chunks, but the join buffer is tiered (4 KiB / 16 KiB / 64 KiB) so small PNG IDAT streams do not pay a full 64 KiB stack frame. A follow-up A/B that forced all stored chunked zlib members onto the direct stored reader was rejected: ReleaseFast `run-chunked-zlib-bench-report -- --repeat 5 --iterations 4000` showed direct geomean around `0.979x`, with `png-indexed-stored-7b-empty` direct throughput falling from about `1654.07` to `1435.63` MiB/s, so the existing `stack_chunked_zlib_tiny_chunk_count` cutoff remains in place. The same benchmark kept a narrower `joinChunks` empty-chunk skip: join throughput improved by about `1.047x` geomean in the A/B, with empty-chunk rows moving roughly `610.12 -> 649.38` MiB/s for `png-rgb8-dynamic-1b-empty` join and `2028.96 -> 2384.63` MiB/s for `png-indexed-stored-7b-empty` join, while preserving direct decode correctness on empty chunk layouts. The gate now also includes `png-indexed-stored-1b-empty` so the pathological one-byte stored split case stays visible beside the 7-byte empty stored row. An attempted `ChunkCursor` micro-optimization that advanced past consumed chunks and skipped empty chunks inside `readByte`/`copyTo` was not kept: the repeat5 chunked benchmark was noise-level overall (`~1.001x` direct geomean) and regressed the newly added one-byte stored empty case (`332.89 -> 329.31` MiB/s), so direct-reader policy needs a more targeted redesign. A later attempt to reuse the already-known `total_len` in stack joins, avoiding a second `chunksTotalLen` scan, was also not kept: join geomean was about `0.987x` and `png-indexed-stored-1b-empty` join fell from roughly `456.02` to `424.37` MiB/s, so the simple `joinChunks` shape remains preferable until a dedicated cursor/copy benchmark justifies a broader rewrite. The follow-up cursor microbenchmark showed that a copy-only empty-chunk advance can improve isolated `copyTo` rows, but the production A/B was still rejected: full `run-chunked-zlib-bench-report -- --repeat 5 --iterations 4000` direct geomean was about `0.996x` and `png-rgba8-stored-256b` direct fell from roughly `10642.72` to `10149.34` MiB/s, so cursor changes must be tied to a more selective stored-reader path. A more selective copy-only empty-chunk advance that triggered only before actual empty chunks was also rejected: repeat5 direct geomean stayed below 1.0 (`~0.997x`) because `png-rgba8-stored-256b` and `png-literal-16b` regressed despite improvements on one-byte empty rows. `run-dictionary-decode-bench-gate` writes and validates `zig-out/vort-dictionary-decode-bench.csv`, measuring allocator-returning, exact-size allocator, and reusable caller-buffer raw/zlib preset-dictionary decode on history-replay, JSON-prefix, and log-prefix fixtures; the history fixture first seeds output from the preset dictionary and then replays from decoded history, while JSON/log rows keep service-style structured payloads visible. Rust deflate decode and encode benchmark scripts accept `--repeat <n>` when
invoked directly; the CSV row records the repeat count and median elapsed time for each
engine/case/mode. The Zig build steps keep `--repeat 1` behavior for smoke speed,
while investigation runs should use repeats such as `--repeat 3` before accepting
small performance deltas.
`run-deflate-decode-stage-report` also accepts forwarded `-- --repeat <n>` and
keeps the median-ish sample by aggregate elapsed score across raw/zlib/gzip
alloc, exact-size, and caller-buffer rows; `run-deflate-decode-stage-report-csv-repeat3`
writes `zig-out/vort-deflate-decode-stage-report-repeat3.csv` for the repeat3
summary path, and `-- --iterations <n>` can keep ad-hoc repeat probes short during
local investigations.

Current deflate tuning keeps speed and ratio goals separate by preset. The
production `.default` path remains the speed/ratio compromise used by zlib-level
6 style callers, while `.best` now spends a measured 256-candidate optimal
parser budget (custom options may request up to the 512-candidate hard cap).

Match replay is another decode hot path: overlapping matches above the
specialized distance-1..4 cases now copy by seeding one distance window and
doubling the initialized prefix. Allocating inflate paths reuse the same doubling
copy after reserving the match span, so long no-dictionary matches avoid
byte-at-a-time ArrayList appends. This improves repeated/source-like matches
without changing fixed, dynamic, zlib, or gzip wire compatibility.

`ci-smoke` is a validation aggregate rather than a full benchmark suite; it
includes bounded reports to catch regressions quickly, while full-corpus or
long-running throughput evidence should still be run as dedicated commands.

## Required evidence before performance claims

For each claim against `zlib`, `zlib-ng`, `zlib-rs`, or `zstd`, record:

- Vort git commit;
- competitor name, version, build flags, and command/API used;
- CPU model, OS, Zig version, optimization mode, and enabled CPU features;
- corpus name and input sizes;
- compression level/strategy/dictionary settings;
- compression throughput, decompression throughput, ratio, compressed bytes, and
  peak or configured memory use;
- correctness gate used after benchmark output was produced.

Compatibility-format benchmarks and native-format benchmarks must be reported
separately.
