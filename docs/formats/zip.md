# ZIP archive support

Vort provides dependency-free, library-first reading and deterministic writing
for common single-disk ZIP32 and ZIP64 archives. The reader parses the ordinary
end-of-central-directory record, the ZIP64 locator/record when present, and the
central directory before exposing entries. Data-descriptor archives therefore
use the authoritative sizes and CRC values instead of trusting incomplete
local headers.

Supported entry methods:

- stored (`method 0`);
- raw Deflate (`method 8`) through the same decoder used by Vort's public raw,
  zlib, and gzip APIs;
- Deflate64 (`method 9`) with its 64 KiB window, 32 distance symbols, and
  extended code-285 match lengths;
- Bzip2 (`method 12`) through Vort's dependency-free Bzip2 codec;
- LZMA (`method 14`) through Vort's LZMA decoder and the ZIP-specific
  properties prefix;
- legacy Zstandard (`method 20`) and its current assignment (`method 93`) as
  complete standard Zstandard frames. Method 20 is accepted for compatibility
  with archives produced before APPNOTE 6.3.8;
- XZ (`method 95`) as a complete XZ stream.

The decoder validates local/central method and filename agreement, ordered
ZIP64 `0x0001` extra fields, exact compressed and uncompressed sizes, complete
Deflate consumption, and IEEE CRC-32. It supports 32- and 64-bit data
descriptors with or without a descriptor signature because extraction
boundaries come from the central directory.

The writer accepts multiple borrowed entries and emits stored, raw-Deflate,
Deflate64, Bzip2, LZMA, legacy/current Zstandard, or XZ members. Select
`.zstandard_legacy` for method 20 and `.zstandard` for method 93; both carry the
same standard Zstandard frame payload. Deflate64 uses a greedy
fixed-Huffman-or-stored baseline with extended 64 KiB distances and records
version-needed 2.1. LZMA entries carry the standard four-byte
ZIP properties prefix, a five-byte LZMA property record, an end marker, general
purpose flag bit 1, and version-needed 6.3. It records CRC-32, sizes, entry
comments, an archive comment, and the UTF-8 general-purpose flag. Its fixed DOS
timestamp is `1980-01-01 00:00:00`, so identical inputs and options produce
identical bytes. Data descriptors are optional and include the standard
descriptor signature when enabled.
`EncodeOptions.zip64` controls archive selection:

- `.auto` emits ZIP32 until an entry count, size, or offset needs ZIP64;
- `.always` emits ZIP64 records and extra fields even for small test archives;
- `.never` rejects values that would require a ZIP64 sentinel.

```zig
const entries = [_]vort.ZipEncodeEntry{
    .{ .name = "plain.bin", .data = plain, .method = .stored },
    .{ .name = "folder/data.txt", .data = text, .method = .deflate },
    .{ .name = "folder/large.bin", .data = large_data, .method = .deflate64 },
    .{ .name = "folder/archive.txt", .data = archive_text, .method = .bzip2 },
    .{ .name = "folder/model.bin", .data = model_data, .method = .lzma },
    .{ .name = "folder/archive.xz", .data = xz_data, .method = .xz },
    .{ .name = "folder/legacy.bin", .data = legacy_data, .method = .zstandard_legacy },
    .{ .name = "folder/frame.bin", .data = frame_data, .method = .zstandard },
};
const zip_bytes = try vort.zipEncodeAlloc(allocator, &entries, .{
    .archive_comment = "generated by Vort",
    .data_descriptor = true,
    .zip64 = .auto,
});
defer allocator.free(zip_bytes);
```

`zipEncodeAppend` builds the archive transactionally: an error leaves the
destination length and bytes unchanged. When the destination already contains
bytes, they are treated as a self-extracting prefix and all stored ZIP offsets
include that prefix.

```zig
const archive = try vort.parseZipArchive(zip_bytes);
defer allocator.free(try archive.entriesAlloc(allocator));

const entry = (try archive.find("folder/data.txt")) orelse
    return error.ZipEntryNotFound;
const decoded = try archive.extractAllocLimited(
    allocator,
    entry,
    64 * 1024 * 1024,
);
defer allocator.free(decoded);
```

Convenience functions `zipExtractEntryInto`, `zipExtractEntryAlloc`,
`zipExtractEntryAllocLimited`, `zipExtractByNameAlloc`, and
`zipExtractByNameAllocLimited` parse and extract in one call. Entry names are
returned as borrowed archive bytes. Vort never automatically joins an entry
name to a filesystem path; callers therefore retain explicit control over
Zip-Slip/path-traversal policy.

Bzip2 inverse BWT, LZMA dictionaries, and XZ blocks need temporary allocation.
The allocating ZIP extraction APIs already use the supplied allocator. For
caller-owned output, use `zipExtractEntryIntoWithAllocator`; the original
no-allocator `zipExtractEntryInto` returns `ZipEntryRequiresAllocator` for
methods 12, 14, and 95.

CLI validation surfaces:

```sh
zig build run -- list-zip-file archive.zip
zig build run -- extract-zip-file archive.zip folder/data.txt output.txt 67108864
zig build run-zip-diff
```

The writer rejects empty names, invalid UTF-8 names/comments when UTF-8 mode is
enabled, fields longer than ZIP's 16-bit name/comment limit, and methods other
than stored/Deflate/Deflate64/Bzip2/LZMA/Zstandard-20/Zstandard-93/XZ. The
reader deliberately
rejects encrypted entries, multi-disk archives, malformed/duplicate ZIP64
extra fields, and compression methods other than
stored/Deflate/Deflate64/Bzip2/LZMA/
Zstandard-20/Zstandard-93/XZ with specific errors.
Addressable entry and archive sizes remain bounded by the target's `usize` and
the caller's available memory. Encryption, split archives, and additional entry
compression methods remain explicit future compatibility increments.

The Deflate64 codec and its raw APIs are described in
[`deflate64.md`](deflate64.md).
